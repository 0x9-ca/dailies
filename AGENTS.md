# Agent Guide

This file helps coding agents quickly understand the repository.

## Product summary

Cloudflare Worker app for discovering daily games. Users can submit links, vote, favorite, report issues, and browse curated lists. Voting works for both authenticated and anonymous users. Editor/admin users moderate content and manage taxonomy/lists. Games have a `paywall` flag indicated by a green `$` badge on cards.

## Core files

- `src/index.ts`: routes, API handlers, SSR rendering, scheduled link check, and client-side inline scripts.
- `src/lib/auth.ts`: session creation/destruction, session middleware, role/auth guards.
- `src/lib/cache.ts`: KV JSON cache helpers and invalidation.
- `src/lib/ranking.ts`: Wilson + freshness/penalty/click/list score helper.
- `src/lib/url.ts`: URL canonicalization and slug helper.
- `src/lib/changelog.ts`: the `/changelog` entries.
- `src/env.ts`: Env type definitions.
- `migrations/*.sql`: D1 schema and seeds.

## Runtime model

- Server: Cloudflare Worker (Hono)
- DB: D1
- Cache: KV
- Background: scheduled handler (`scheduled`, daily cron `15 8 * * *`) for link-health checks, score recalculation and a backstop flush of the Discord announcement queue; the `AnnouncementScheduler` Durable Object's alarm sends the announcements

## Security model

- Cookie sessions (`SESSION_SECRET` hashed session tokens in D1)
- Role checks (`user`, `editor`, `admin`)
- CSRF enforcement on mutating `/api/*` requests with double-submit cookie (`csrf_token` + `x-csrf-token`)
- D1-backed fixed-window rate limiting for submit/vote/report (submissions: 10/hour per user or anonymous visitor; admins are exempt)

## Key behaviors

- Editor/admin submissions are auto-approved.
- Standard user submissions are `pending` until moderated.
- Private curated lists are visible to owner + editor/admin only (and the list's tagged Twitch user).
- Curated lists can be tagged with a Twitch user by editors/admins (`PATCH /api/lists/:id/twitch`, resolved via Helix to a stable `twitch_user_id`). Tagged lists show a blue verified check and a Twitch channel button. The matching Twitch-login user (via `oauth_accounts`) can edit the list's games, title and description (`requireListEditor`), but not slug, visibility, deletion, or the tag itself.
- Favorites support manual ordering and weekday masks.
- Anonymous favorites are local-first and can sync after login; anonymous votes are limited to one vote per game per IP hash.
- Login supports Discord and Twitch OAuth via `/login` (shared helpers `beginOAuth`/`readOAuthCallback`/`exchangeOAuthCode`/`revokeOAuthToken`). Provider access tokens are revoked right after the profile read and never stored (only the profile picture URL is kept, see public profiles). Discord roles are re-synced on every login. Logout is `POST /auth/logout`. Twitch sign-in requests no scopes (no email) and always yields role `user`; the only place Twitch is asked for scopes is the opt-in Fan-dles check below. A first sign-in creates an account with a placeholder email; from Settings, a signed-in user can link the other provider (`POST /auth/:provider/link`, intent carried in the OAuth state cookie). If that provider account already has its own user, `mergeUsers()` moves everything onto the signed-in user and deletes the other. Unlink is `DELETE /api/me/accounts/:provider` (never the last one; unlinking Discord resets the role to `user`). Twitch needs `OAUTH_TWITCH_CLIENT_ID` (var) and `OAUTH_TWITCH_CLIENT_SECRET` (secret); the button is hidden when the client ID is unset.
- Games can be marked as `paywall` by editors/admins; a green `$` badge renders after the title on all card views.
- Server-time resets can carry a `reset_timezone` (IANA name; only kept when `reset_basis = server`, null means UTC). Reset sort converts via per-zone UTC offsets computed in the Worker.
- Click tracking: `POST /api/games/:id/click` increments `click_count`; score computation factors in click count and list membership.
- Logged-out views of `/`, `/games`, `/games/:slug`, `/lists`, `/lists/:slug`, `/mod-log` and `/changelog` are cached at the edge for 60s (`PUBLIC_CACHE_PATHS`, `X-Page-Cache: HIT|MISS`). Requests with a session cookie or the `dgl_voted` cookie (set after a vote) bypass it. Not in development.
- Open pages reload themselves after a deploy: every page has `<meta name="app-version">` (the Cloudflare version id from the `CF_VERSION_METADATA` binding, see `appVersion()`), and `APP_UPDATE_SCRIPT` polls `GET /api/version` once a minute while visible (and on tab focus). It never reloads while a text field is focused (waits until it's left) or after the visitor typed into a form (shows a notice instead), and reloads at most once per new version per tab. The edge page cache is keyed by version, so the reload always gets new HTML. Any version change counts, including `wrangler secret put` and trigger changes.
- Curated list pages (view mode) update live: every 30s while visible they compare `GET /api/lists/:slug` with the rendered order; on a change they fetch a fresh render of the page (unique `?live=` query, so not the edge cache), fade out removed rows (`.row-leave`), add new ones (`.row-enter`, bound via `dglBindGameRows`) and re-apply the chosen sort. The list sort (`LIST_SORT_SCRIPT`, `renderListSortControl({ votes: true })` on curated lists only) offers default, resetting soonest, highest % upvoted and most upvotes; vote orders read the counts shown in each row.
- Vote counts update live: `GAME_ACTIONS_SCRIPT` polls `GET /api/games/vote-counts` every 20s while the tab is visible for every `[data-game-row]`/`[data-vote-counts]` on the page and updates `[data-up-count]`, `[data-down-count]`, `[data-liked]` and `[data-rating]` in place with a short `.count-bump` pulse. Games the visitor voted on in the last 30s are skipped so a cached answer can't undo their vote. Keep those data attributes on any new place that shows counts.
- Curated lists take suggestions (`list_suggestions`, `list_suggestion_votes`, `list_blocked_games`): viewers (signed in, or logged out and counted by hashed IP like anonymous game votes; `list_suggestion_votes.voter_key` is `user:<id>` or `anon:<hash>`) suggest a game from the panel on the list page (the Suggestions tab, see the Fan-dles bullet for the layout; the panel shows the top 5 with a "Show all (N)" toggle, one muted line of categories per row, and the suggest input on top) and agree with others' suggestions, one vote each (the suggester's included); suggesting an already-suggested game counts as a vote, and a game already on the list is refused with an error toast. Ordered by votes, then age. Editors, admins and the list's Twitch owner can turn suggestions off per list (`curated_lists.suggestions_enabled`, the "Allow suggestions" checkbox in edit mode, `PATCH /api/lists/:id { suggestionsEnabled }`): the panel disappears (open pages drop it on their next refresh), suggesting and voting return 403 `code: "disabled"`, and existing suggestions are kept for when it's turned back on. They also add a suggestion to the end of the list or dismiss it. A dismissed suggestion, or a game removed from the list, goes into `list_blocked_games` and can't be suggested there again until it's added to the list directly. The edge-cached logged-out page carries no per-visitor vote state, so it loads the visitor's own votes from `GET /api/lists/:id/suggestions` on load; the panel refreshes every 30s. Anyone can take their vote back; taking back a suggestion's last vote deletes the suggestion without blocking the game. As with game votes, anonymous votes stay separate from an account after login. `mergeUsers()` moves suggestion votes.
- Cards with a reset time show whether this browser has played the game since its last reset: opening a game (a card's game link, or the Play button on its page, to the game's own site) is stored in localStorage `dgl_played_v1` (`{ gameId: epoch ms }`, pruned after 3 days; `window.dglMarkPlayed(id)`). `RESET_LOCALIZE_SCRIPT` then adds `.played` (faded card) when that time is after the last reset, and `.reset-soon` (red reset bar, `--reset-bar-soon`) when it isn't and the reset is under two hours away. Recomputed every minute, on tab focus and when another tab records a play. Games without a reset time are never marked. It's per browser, not synced to the account.
- Rotation daily progress (client-side, `DAILY_PROGRESS_SCRIPT`, `/me/rotation` both render paths; not on the shared page): "N of M played today" bar, "Play next" (first unplayed row in DOM order, opens its site and calls `dglMarkPlayed`) and a streak in localStorage `dgl_streak_v1` (`{ last: "YYYY-MM-DD", count }`, local dates; shown from 2 days when last is today or yesterday). Today's games = rows whose `data-weekday-mask` has today's bit (Monday = bit 0; local favorites have no mask = every day). Played uses `window.dglIsPlayed` (same reset rule as `.played`, no reset time = since local midnight); it recomputes through `window.dglPlayedHooks`, run by `dglLocalizeResets`.
- Header search typeahead (script in `layout()`): from 2 characters (120ms debounce) shows up to 8 games (prefix matches first, then substring) from `GET /api/games/titles` (`{ games: [{ id, slug, title }] }`), fetched on first focus and kept in memory and sessionStorage `dgl_titles_v1`. ARIA combobox on `#header-search-input`, listbox `#header-search-list` (`.search-suggest`); Escape closes the list before the existing Escape behavior.
- Shared rotation helpers (`ROTATION_TODAY_SCRIPT`, in `<head>` on every page): `window.dglProgressWidget(box, getRows)` (the daily progress widget logic, used by `/me/rotation` and the home strip), `window.dglTodayRotation.get(maxAgeMs)` (today's games with links and resets: `GET /api/me/session` says whether a session exists (always 200, `no-store`), then `GET /api/me/rotation?weekday=` or local favorites, plus `GET /api/games/rotation-info`) and `window.dglDateKey`. The home page (edge-cached) renders only a hidden `#daily-progress` strip (`HOME_ROTATION_MARKUP`) that the browser fills for everyone.
- Reset reminders (opt-in, `window.dglReminders`): the "Remind me before resets" toggle on `/me/rotation` (hidden without `Notification`) stores `dgl_reminders_v1` (`{ on, minutes: 30|60|120 }`) and asks for permission (reverts with a toast if denied). While on, every page checks on each `dglPlayedHooks` tick (rotation data refetched at most every 10 minutes) and shows one `Notification` per unplayed game per reset within `minutes`, deduped in `dgl_reminded_v1` (`{ gameId: reset epoch ms }`, pruned after 2 days). One tab notifies at a time via the `dgl_reminder_lock_v1` timestamp lock. A click focuses the tab and opens the game page.
- Play history heatmap on `/me/rotation`: `dglMarkPlayed` adds one to `dgl_play_log_v1` (`{ "YYYY-MM-DD": games }`, local dates, pruned after 365 days) the first time a game is played each local day. A 12-week grid (Monday on top, 4 levels via `--heat-1..4`) under the progress widget, hidden when nothing was played in those weeks.
- Copy as text (`#copy-text-btn` on both `/me/rotation` paths, wired in `DAILY_PROGRESS_SCRIPT`): today's games (same weekday rule as the progress bar) as plain text, "My dailies for Thu, Oct 30:" then `N. Title ✓ — <origin>/games/<slug>` (✓ = `dglIsPlayed`). Clipboard API, with a hidden-textarea fallback. Signed-in rows carry `data-game-slug`/`data-game-title` for it.
- Hidden games ("Not interested"): localStorage `dgl_hidden_v1` (array of game ids, `window.dglHidden`, `HIDDEN_GAMES_SCRIPT` in `<head>`). Only cards rendered with `renderCompactGameList(..., { hideable: true })` (`data-hide-id`; `/` and `/games`) get the eye button; a generated `<style>` hides them before first paint, so nothing is rendered server-side (edge cache safe). The hide shows an Undo toast (`appToast(msg, level, ms, { label, onClick })`). Unhide from "Hidden games (N) · Show" under `/games` (`html.dgl-show-hidden` reveals them) or the Hidden games section of `/me/settings` (titles from `GET /api/games/titles`).
- Cards show "N% liked" (upvote share) and a live reset countdown ("Resets in 3h 12m") instead of the internal score; the score is still used for sorting.
- Short host (`SHORT_URL`, `src/lib/origins.ts`): serves the same site as `APP_URL`; SEO/external URLs (canonical, og, JSON-LD, sitemap, feed, llms.txt, Discord, claim names) stay on `APP_URL`, and production adds `X-Robots-Tag: noindex` on the short host. OAuth `redirect_uri` (begin and token exchange) uses the request origin when allowed, so a sign-in stays on one host; cookies are host-only (sessions are not shared between hosts). `/c/:slug`, `/g/:slug`, `/r/:token` 301 (relative, query kept) to `/lists`, `/games`, `/rotation`. Share links, Copy as text, the developer link and the stream bar use short URLs via `window.DGL_SHORT_ORIGIN`.
- Non-production environments send `X-Robots-Tag: noindex` and a `Disallow: /` robots.txt; workers.dev and preview URLs are off for staging and production.
- Deployed environments redirect plain HTTP to HTTPS (301, or 308 for non-GET) and every response carries HSTS (not in dev), `nosniff`, `Referrer-Policy` and `frame-ancestors 'none'`/`X-Frame-Options: DENY` (first middleware in `src/index.ts`).
- Missing pages (unknown game, list, category slug, page number past the end, unmatched route) render `notFoundPage()`, an HTML 404 with `noindex`; unmatched `/api/*` routes return JSON 404.
- SEO data per page: game pages carry `VideoGame` JSON-LD and an "About" facts section (category descriptions, rating, public lists featuring the game, listed-since date); category and list pages carry an `ItemList` (`gameItemListLd()`); every page carries `WebSite` and `Organization`. List meta descriptions fall back to `listMetaDescription()` when a list has no description.
- The submit form has an optional "How to play" box (`howToPlay`, same 2000-character limit, stored in `games.how_to_play`); editors see it in the submissions queue and can edit it like any editor-written text.
- Games have an optional editor-written `how_to_play` (plain text, max 2000 chars, blank line = new paragraph), edited in the game page's admin form and shown at the top of its "About" section.
- Each game page's `og:image` is `/og/games/<slug>.png?v=<hash>`, drawn on demand by `src/lib/og.ts` (satori + resvg WASM via `@cf-wasm/og`, Manrope from `src/lib/og-fonts.ts`) and edge-cached for a day. `v` changes when the title, description, categories or paywall flag change. A render failure falls back to the site image.
- When a game becomes public for the first time (editor/admin submission, single or bulk approve, or a status change to approved in the edit form; not a restore of a disabled game), `announceNewGames()` posts "New game: **Title**" plus its page link to Discord #dailies via the `DISCORD_NEW_GAME_WEBHOOK_URL` secret, pinging role `DISCORD_ROLE_DLE_ENJOYER` (`allowed_mentions` limits pings to that role). Announcements are batched: approvals add the game to `announcement_queue` (`queueNewGameAnnouncements()`), which sets the alarm of the `AnnouncementScheduler` Durable Object (binding `ANNOUNCER`, one instance named `new-games`) to 3 minutes after the latest approval, capped at 15 minutes after the first of the batch. The alarm runs `flushAnnouncementQueue()`, which posts the whole queue as one message. A failed send is retried every minute and dropped after an hour; the daily cron also flushes anything left over, and an editor or admin opening any `/admin` page starts the timer if games are queued without one. (An every-minute cron was tried first and Cloudflare never ran it on this account.) Nothing is queued when the webhook is unset (staging and dev by default). New approval paths must pass the ids `logGameEvents()` returns to `queueNewGameAnnouncements()`.
- Developer claims (`game_claims`, `src/lib/claims.ts`): a signed-in user claims a game from its page and proves it by putting their per-claim token in a `<meta name="0x9dles-verify">` tag on the game's URL or in `/.well-known/0x9dles.txt` on its origin (names get a `-stg`/`-dev` suffix outside production, see `claimNames()`; the Worker fetches both; `POST /api/games/:id/claim/verify`), or submits evidence for an editor to approve in `/admin/claims` (method `manual`). A verified claim (one per game) shows a blue check and the developer's name on the game page and lets that user edit title, URL, description, how-to-play, reset and paywall through `PUT /api/games/:id/developer-update` (not status, NSFW or categories; staff keep the admin form). Any change to a game's URL re-checks its verified claim: a developer edit must already carry the token at the new address; an admin edit fires `reverifyClaimsForGame()`, which drops a claim without the token back to `pending`. The daily cron (`runClaimRechecks`) revokes a tag claim after 3 definite misses in a row (unreachable sites don't count). Verified/removed events appear in `/mod-log`. A pending game's page is visible to its submitter (noindex) so they can claim it. The submit form asks "Did you make this game?": a signed-in "yes" sends `isDeveloper: true`, `POST /api/games` starts the claim and the form sends them to the game's page to finish it; signed out, the yes shows Discord/Twitch sign-in links (`/auth/<provider>?next=/submit`, a same-site path kept in the `login_next` cookie, see `safeNextPath()`) and the form is kept in localStorage (`dgl_submit_draft`, one hour) and restored on return. A duplicate-URL 409 includes the existing game's `slug` (listed games only) so its developer can claim it. A verified developer sees a "Help players find your game" panel with a link back to the game's page to copy.
- Dle Developer Discord role (`src/lib/developer-role.ts`, table `discord_role_grants`): a user with a verified claim and a linked Discord account gets the role `DISCORD_ROLE_DLE_DEVELOPER` in our server if they are a member. Only a bot with Manage Roles can grant a role to someone else, so it needs the `DISCORD_BOT_TOKEN` secret and is off without it (staging gets no token unless `DISCORD_BOT_TOKEN_STAGING` is set, because staging shares the production server; no other code path changes when it's off). `markClaimVerified()` (every way of becoming verified: tag, file, or an editor's approval) and every sign-in/link (`completeOAuth()`) call `queueDeveloperRole()`, which adds the user's row and kicks the `DeveloperRoleSync` Durable Object (binding `ROLE_SYNC`, one instance named `developers`). Only that object talks to Discord, so calls are serial and 429s (`retry_after`) are handled in one place. Its alarm checks each waiting developer: `GET /guilds/:id/members/:user` (404 = not in the server yet, a cheap check), then `PUT .../roles/:role` if they lack it. Developers not yet in the server are re-checked every 10 minutes for their first day, hourly for a week, then every 6 hours (`DEVELOPER_ROLE_RECHECK_SECONDS` overrides, for tests); a sign-in checks at once. The alarm only fires while someone is waiting. A Discord 401/403 (bad token, no Manage Roles, or the bot's role below Dle Developer) is logged and retried hourly. The role is only ever added: a developer who loses their verified claims, or a moderator who removes the role from someone still in the server, is left alone. The daily cron (`recheckGrantedRoles`) resets anyone who has left (or rejoined since being given the role) so they get it again. Only verified claims count, so a claim revoked before the user joins never grants it. For local tests, point `DISCORD_API_BASE` (and `DISCORD_BOT_TOKEN`) at a fake Discord with `wrangler dev --var`.
- Public profiles are opt-in (`users.profile_public`, `profile_handle`, `profile_show_rotation`, `profile_show_twitch`, `profile_avatar_provider`; set in Settings via `PUT /api/me/public-profile`). `GET /u/:handle` shows the display name, avatar, badges (Admin/Editor from the role, Verified developer when the user has a verified claim, Twitch channel), the games they're verified developer of (`listGames({ developerUserId })`) and optionally their rotation. A non-public profile is a 404 to everyone but its owner (preview). The page is never edge-cached (so switching a profile off takes effect at once) and is `noindex`. Avatars are the providers' public CDN image URLs saved on `oauth_accounts.avatar_url` at every sign-in/link (`saveOAuthAvatar`; only `cdn.discordapp.com` and `static-cdn.jtvnw.net` are rendered, see `safeAvatarUrl`), so they only appear after the user next signs in; they are not tokens. The Twitch channel name is looked up from the stored Twitch id (`getTwitchLoginById`, KV-cached 6h) so renames are followed. Game pages link a verified developer's name to their profile when it is public. Game cards, list and rotation rows and list suggestions show the same developer as a blue outlined pill after the category pills (`getDevelopersForGames()` batches the lookup, `renderDeveloperChip()` renders it; the logged-out rotation gets it from `GET /api/games/categories?withDevelopers=1`). It shows for every verified developer: a link to `/u/<handle>` when their profile is public, otherwise plain text (`.dev-pill-static`, taps pass through to the card). It is hidden on that developer's own profile page. `PILL_FIT_SCRIPT` (every page) keeps each `.category-pills` group to two lines: trailing category pills get `hidden` behind a `+N` button (`.pill-more`, toggles `data-expanded`), never the developer pill. It refits on width changes (ResizeObserver) and on pills added by other scripts (MutationObserver), so new places that render pills just need the `.category-pills` class.
- `/u/:handle` "Lists": the owner's public curated lists with games (creator list included), each linking to `/lists/<slug>` with the same verified check as `/lists`. Hidden when none.
- Reduced motion: one `@media (prefers-reduced-motion: reduce)` block at the end of `layout()`'s CSS sets animation and transition durations to 0.01ms and `scroll-behavior: auto`. Scripts must not depend on animation events alone; hidden cards and removed rows finish on timers.
- Verified creators (`users.creator_type`: `affiliate`/`partner` from Twitch's `broadcaster_type`, read at every Twitch sign-in/link by `syncCreatorStatus()`, or `manual`, granted by an admin at `/admin/creators` (admins only, not editors) either to an existing account (`POST /api/admin/users/:id/creator`) or to a Twitch username (`POST /api/admin/creators/twitch`, stored in `creator_allowlist`: an existing account with that Twitch id becomes a creator at once, otherwise at their first Twitch sign-in; removing the entry drops a manual status but never an affiliate or partner one). A streamer verified this way who has no account yet is verified straight away on any public editor-tagged list for their Twitch id (`VERIFIED_LIST_SQL`: the check, and Fan-dles on that list, until they have a list of their own); at their first sign-in `ensureCreatorList()` makes their own list, copies the games, and moves the Fan-dles members and hidden games over). A creator gets one list of their own (`curated_lists.kind = 'creator'`, one per owner), made by `ensureCreatorList()` the first time they qualify: public, suggestions open, tagged with their Twitch channel, and with the games of any editor-tagged list for the same Twitch id copied in (oldest list first, deduped; the originals stay). The list is theirs from then on: losing creator status removes the check and their edit rights (`isCreatorListOwner()`) but never makes it private. The owner can edit it, set it public/private (`PATCH /api/lists/:id/visibility`) and toggle suggestions; deleting, slug and the Twitch tag stay staff-only. Personal favorites/rotation are unchanged and stay private. Creator lists with no games are left off `/lists`, the sitemap and `llms.txt` (and are `noindex`). Unlinking Twitch clears a Twitch-derived status and the list's channel tag; `mergeUsers()` keeps one creator list. One person can have at most 20 open suggestions per list (`MAX_OPEN_SUGGESTIONS_PER_PERSON`).
- Fan-dles (`fandle_members`, `fandle_hidden`, `curated_lists.fandles_enabled`, `src/lib/fandles.ts`): a section on a public creator list (tagged with a Twitch channel) showing games by that streamer's community. A verified developer opts in from the list page ("Check with Twitch", `POST /auth/twitch/fandle`), which runs a separate Twitch authorization asking for `user:read:follows user:read:subscriptions` (the same `/auth/twitch/callback`, with intent `fandle` and the list slug in the `fandle_list` cookie; ordinary logins still ask for no scopes). The callback links the Twitch account if needed, asks Twitch only whether this user follows or subscribes to that one channel (`fetchTwitchRelationship()`), revokes the token and stores just the result: a subscriber joins at once, a follower after `FANDLE_MIN_FOLLOW_DAYS` (7) days of following (Twitch's `followed_at`). A check never runs out by default (the developer can leave); an admin can set "check again after N days" at `/admin/settings` (`fandle_membership_days`, applied to `fandle_members.verified_at` at read time by `fandleActiveSql()`, so changing it affects existing memberships; `expires_at` is always `FANDLE_NO_EXPIRY`). The section shows every member's verified, approved games (best score first), minus hidden ones (a game also on the list's main section still shows in Fan-dles). Layout (`.list-layout`, curated list pages with suggestions and/or Fan-dles; `.has-fandles` / `.no-suggest` mark which sections exist): from 900px the list (`.list-main`, hero, up to 1480-1680px wide pages) sits beside ONE sticky right-hand sidebar (`.list-sidebar`, 320-360px) whose tabs (`.side-tabs`, `data-side` on the layout) switch between Fan-dles and Suggestions, each with a count pill; a button (`#side-toggle`) collapses it to a 64px rail of tab icons and counts (a rail tab re-opens it). The collapse is remembered in localStorage `dgl_list_sidebar_v1` (`collapsed`/`expanded`) and applied before first paint by `LIST_PAGE_HEAD_SCRIPT` (class `dgl-sb-collapsed` on `<html>`; nothing per visitor is rendered, the page is edge-cached). Under 900px the sidebar dissolves into the phone tabs instead (`.list-tabs`, `data-tab`): List, Fan-dles (if shown) and Suggestions (if on), each with its count in a pill. On both, `#fandles` / `#suggest` in the URL pick a tab (on desktop it also opens a collapsed sidebar), and a Fan-dles result message opens the Fan-dles tab. Its cards have no vote buttons, and the streamer, editors and admins get an "Add" button that copies a game onto the main list (`POST /api/lists/:id/items`) when it isn't there already. There are no caps by default; an admin can set a most-per-developer and a most-in-total limit at the same page (`site_settings` keys `fandle_max_per_developer` / `fandle_max_shown`, read by `getFandleLimits()`; empty = no limit, and `FANDLE_HARD_MAX_SHOWN` (100) only guards page size when no total is set). The streamer (or staff) can switch Fan-dles off, and hide individual games in the list's edit mode (`PUT /api/lists/:id/fandles/:gameId/hidden`); a member can leave (`DELETE /api/lists/:id/fandle-membership`). Admins (only) can add a verified developer to a list's community by hand, with no Twitch check, from the list's edit page (`GET /api/admin/developers?q=` to search, `POST /api/lists/:id/fandle-members {userId}`, `DELETE /api/lists/:id/fandle-members/:userId`; source `manual`, which never lapses) and can remove any member the same way. Development: `/auth/mock-fandle/:slug?followDays=10&sub=1` stands in for the Twitch check.
- List page header and stream mode (`LIST_PAGE_SCRIPT`, `renderStreamBar()`; view mode only): the header is one row (title, check, Twitch button, then Share, Edit, Add all, Stream mode; the sort sits in the Games bar above the rows). When they don't fit on one line (and on phones) everything except Share and Edit moves into a "⋯" menu (`aria-expanded`, `role=menu`, Escape and outside click close it, arrow keys move). Descriptions clamp to 3 lines with a More button. Stream mode (`html.dgl-stream`) hides the site header/footer, sidebar and row controls and shows numbered large-type rows, reset countdowns, and a bottom bar with "Suggest games at <APP_URL host>/lists/<slug>" plus the top 3 suggestions (kept current by the suggestions script, so live refresh keeps working). ## Scoring

Game score is computed from: Wilson lower bound of vote ratio, freshness bonus, click boost (+0.003/click, max +0.30), and list membership boost (+0.10/list, max +0.20). Penalties apply for reports and link failures.

## Rotation export/import

- **Export** downloads a JSON file with `{ version: 1, items: [{ id, slug, title }] }`.
- **Import** reads a JSON file, validates format, and adds non-duplicate games.
- **Logged-in users:** export/import via `GET /api/me/favorites/export` and `POST /api/me/favorites/import`. Server-side DB queries. Export also includes `position` and `weekdayMask` per item.
- **Anonymous users:** export/import is entirely client-side via localStorage. No API calls.
- Both flows are additive (duplicates are skipped by `INSERT OR IGNORE`).

## Favorites data model

- `favorites` table: `user_id`, `game_id`, `position`, `weekday_mask` (bitmask, 127=all days).
- `anonymous_favorites` table: `anon_id`, `game_id` (no position or weekday_mask).
- Local favorites in localStorage key `dgl_local_favorites_v1`: `[{ id, slug, title }]`.

## Safe editing notes for agents

- Keep SQL parameterized with D1 prepared statements.
- Handlers for edge-cached pages must not render per-visitor state for logged-out requests when `c.get("publicCache")` is true; use `getViewerGameState()` for votes/favorites, which already handles this.
- Use `renderDetailsLink()` for links to game pages from cards (a real `<a>`, so crawlers can follow it) and `class="narrow"` on `<main>` for text/list pages.
- Game cards and rows are tappable: the container has `card-click` and the game-name link `card-link`, whose overlay covers the card. Anything else clickable inside (buttons, `.btn-details`, `.category-pill`, `.drag`) must sit above it (see the `.card-click` CSS). Don't use it where rows are dragged by the whole row (list edit mode). The logged-out rotation gets game links from `GET /api/games/rotation-info`.
- Embed server values in inline `<script>` blocks with `scriptJson(...)`, never raw `JSON.stringify(...)`; in client code, put user text in the DOM with `textContent`, not `innerHTML`.
- Mock login (`/auth/mock-login/:role`) only works when `APP_ENV` is development and the request host matches `APP_URL`. Production has its own D1/KV; staging and the default (dev) config use a separate staging D1/KV. In `wrangler d1` commands use the `DB` binding with `--env`, never the database name (a name can resolve to production).
- Update both server route behavior and inline client script behavior together.
- If adding mutating APIs, ensure CSRF and auth/role checks are included.
- If adding public list queries, consider cache invalidation with `invalidateGameCaches`.
- The `/me/rotation` page has separate rendering paths for anonymous (localStorage) and authenticated (DB) users — update both if changing rotation UI.
- Inline `<script>` blocks in `src/index.ts` handle client-side rendering for rotation and game list pages. These are not separate files.
- Client-side voting and favoriting (account and local/anonymous), the local favorites store, and the local-to-account import all go through `window.dglGames` (`GAME_ACTIONS_SCRIPT`, loaded in `<head>` by `layout()`). Use it rather than calling those APIs or touching `dgl_local_favorites_v1` directly.
- The `game_categories` table has a required `assigned_by_user_id` column — always include it in INSERT statements.
